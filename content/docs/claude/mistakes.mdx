<InOneMinute>

- Most mistakes on this page come from treating one tool like another — `CLAUDE.md` like a hook, a Project like a skill, a fenced example like something that syncs itself.
- Two terms circulate that are not real: "traits" and "modules." Neither is part of any official spec.
- This page is deliberately negative — it exists to catch the things a first read of the other pages will not.

</InOneMinute>

## Configuration mistakes

<Callout type="danger" title="Relying on CLAUDE.md for a hard rule">

`CLAUDE.md` is context Claude reads, not a rule it is forced to obey. A rule that must never be broken belongs in a [hook](/docs/claude/hooks) instead — see the exit-code table there for exactly how a hook enforces it.

</Callout>

<Callout type="danger" title="A bloated CLAUDE.md">

Files over 200 lines consume more context and measurably dilute how closely Claude follows any single instruction in them. If a section has grown into numbered steps, it has grown into a [skill](/docs/claude/skills) — move it.

</Callout>

<Callout type="danger" title="Putting shared team policy in a local-only file">

`.claude/settings.local.json` is auto-gitignored — nothing in it reaches your teammates. Shared permissions, hooks, and MCP servers belong in the committed `.claude/settings.json` instead.

</Callout>

<Callout type="danger" title="Assuming a skill syncs across surfaces">

It does not. A skill in your repo, a skill uploaded to claude.ai, and a skill uploaded to the API are three separate uploads. Keep the source in git as the one canonical copy, and treat each surface as a deploy target.

</Callout>

<Callout type="danger" title="Using non-portable skill fields in a shared skill">

Claude Code understands extra frontmatter fields — `model`, `effort`, `disable-model-invocation`, and others — beyond the six the open spec defines. A skill using them may error if it is uploaded somewhere that only expects the spec's six fields. Stick to the six if the skill needs to travel.

</Callout>

<Callout type="danger" title="Under-governing third-party skills">

A skill runs code. Vet one before installing it from someone you do not know, the same way you would vet a new dependency — and turn on skill content scanning at the organization level if it is available on your plan.

</Callout>

## Two terms that are not real

<Callout type="warn" title={'"Traits" is not an official feature'}>

There is no `traits:` field in the Agent Skills spec, in Claude Code, or in the apps. The confusion usually comes from subagents being informally described as having a "persona," or from a third-party skill author inventing their own `traits:` key as a personal convention. The actual, supported ways to control tone and persona are [Output Styles and subagent prompts](/docs/claude/subagents) in Claude Code, and Styles plus your profile preferences in [the apps](/docs/claude/apps).

</Callout>

<Callout type="warn" title={'"Modules" is not a real skill directory'}>

The three canonical, recognized folders inside a skill are `scripts/`, `references/`, and `assets/` — see [Skills](/docs/claude/skills). You can create other folders, but nothing looks for one named `modules/` specifically.

</Callout>

## Where to check when in doubt

If a specific detail on any page here — a settings key, a hook event name, a version number — matters for something you are about to ship, verify it against Anthropic's own current documentation first. This reference is checked against the source it cites (see each page's **Last reviewed** line), but Claude's customization surface changes quickly, and a detail correct on the date reviewed can drift.
