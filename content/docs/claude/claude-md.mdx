<InOneMinute>

- `CLAUDE.md` loads at the start of every conversation. It is context Claude reads, not a rule it enforces.
- Two versions exist: `./CLAUDE.md` (your team's, in git) and `~/.claude/CLAUDE.md` (yours, every project).
- Keep it short. Files over 200 lines cost context and dilute how closely Claude follows any single line.
- Do not write a hard rule here and expect it to always hold. A rule that must never be broken belongs in a [hook](/docs/claude/hooks) instead.

</InOneMinute>

## What it is

`CLAUDE.md` is durable project memory: the facts, conventions, and pitfalls you would otherwise explain at the start of every session. Claude Code reads it automatically, before you type anything.

It is one piece of a larger memory system, alongside auto memory (notes Claude writes itself) and `.claude/rules/` (memory scoped to one part of your project). This page covers the file itself. See [Memory management](/docs/claude/memory) for how all three fit together.

## The smallest working example

<CodeBlock language="markdown" filename="CLAUDE.md" code={`# Project conventions

- Use pnpm, not npm.
- Run \`pnpm test\` before every commit. Do not skip this.
- API routes live in app/api/, not pages/api/.
- Never edit generated files in db/migrations/generated/.`} />

- One concern per line. Each bullet is a fact or a pitfall, not a paragraph of explanation.
- No history, no "as you know." Claude does not need the reasoning, just the rule.

<CheckItWorked>
Open the project in Claude Code and ask "what do you know about this project?" It should repeat your conventions back without you pasting them.
</CheckItWorked>

## How it behaves

1. **Files higher in the hierarchy load first.** An enterprise-managed `CLAUDE.md`, if your organization has one, loads before your project's, which loads before your personal one.
2. **Claude Code walks the directory tree.** It reads project-level files in and above your working directory, and lazily loads any `CLAUDE.md` in a subdirectory when Claude actually touches a file there.
3. **`@path/to/file` imports another file's content.** The standard way to pull in personal preferences without committing them is `@~/.claude/my-preferences.md` inside your project's `CLAUDE.md`.
4. **Imports do not save context.** Splitting instructions across multiple imported files helps you organize them, but every imported file still loads at launch. It is not lazy.
5. **`CLAUDE.local.md` is deprecated.** Use an import to a home-directory file instead. Imports survive git worktrees in a way a local-only file does not.

<Callout type="note" title="Working with AGENTS.md">

Claude Code does not read `AGENTS.md` directly. If your team already maintains one for other tools, the standard pattern is a `CLAUDE.md` that does `@AGENTS.md`. That gives you one shared source of truth, plus a thin file for anything Claude-specific.

</Callout>

## When not to use it

A rule that must never be broken, not "usually followed," but never, belongs in a [hook](/docs/claude/hooks), which runs as a command rather than being read as advice. A multi-step procedure you only need occasionally belongs in a [skill](/docs/claude/skills), so it does not cost context on every unrelated message.
